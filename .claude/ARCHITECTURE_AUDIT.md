## 1. Вердикт

**Домен здоров. Больна презентация.**

Доменный слой — образцовый: `grep` по `domain/**` не нашёл **ни одного** импорта `data`/`ui`/Ktor/Compose.
Правило зависимостей соблюдено, порты компактны, конечный автомат data-driven. Ломать там нечего.

Вся боль сосредоточена в двух UI-файлах, где лежит **29% кодовой базы**. `ChatState` — не state-holder,
а god-object: 1945 строк, 94 observable-поля, 116 функций, 49 маркеров «День NN» и минимум 12 несвязанных
зон ответственности. Он же de-facto composition root: сам конструирует Ktor-клиенты и лазит в файловую
систему — прямо нарушая собственное правило проекта из `CLAUDE.md` «не тащить HTTP/Ktor/файлы в ui».

Причина не в неаккуратности, а в **режиме роста**: проект строился по фиче в день, и каждая новая панель
аддитивно приклеивала свои поля и методы в один класс. Для скорости курса это работало; как архитектура
уровня senior/lead — не выдерживает.

**Живая иллюстрация, а не теория.** Во время работы над страновым скоупом я добавил в `ChatState` свойство
`agentRagOptions` и использовал его в `rebuildAgent()`. Приложение упало при старте:

```
NullPointerException: parameter options is null
  at ChatState.rebuildAgent(ChatState.kt:1922) ← ChatState.<init>(ChatState.kt:263)
```

`rebuildAgent()` вызывается из `init`, а свойство объявлено на 700 строк ниже — на тот момент оно ещё `null`.
`compileKotlin` такое не ловит. В классе на 200 строк эта ошибка невозможна физически: `init` и все поля
видны на одном экране. Это и есть цена god-object'а, выраженная в упавшем окне (исправлено в `ee44bc7`).

## 3. Нарушения

### 3.1 SRP — «один модуль, одна причина изменения»

Мартин формулирует SRP через **акторов**, а не через «класс делает одну вещь»: *«Gather together the things
that change for the same reasons. Separate those things that change for different reasons»*. У `ChatState`
таких причин минимум двенадцать, и каждая — отдельный источник запросов на изменение:

| Зона | Строки |
|---|---|
| аккаунты / онбординг | 291–380 |
| отправка чата | 382–427 |
| dev-ассистент `/help` | 429–575 |
| оркестрация задачи | 577–744 |
| MCP-панель | 745–953 |
| RAG-панель | 954–1047 |
| панель локальной LLM | 1048–1160 |
| панель HTTP-сервиса | 1161–1258 |
| RAG-эвалы | 1259–1433 |
| коннекторы / skills / prompt-tune | 1434–1573 |
| интервью | 1574–1677 |
| инварианты | 1844–1862 |

**Чем вредит.** Любая фича трогает один файл → конфликты слияния гарантированы. Ни одну панель нельзя
протестировать без всего графа зависимостей. 94 состояния в одном скоупе делают инварианты состояния
непроверяемыми: есть фактические межпанельные записи — `optimizeCompare()` (День 29) пишет в `localLlmNote`
(поле панели Дня 26), `openRag()` пишет в `localLlmModels`, а `ragNote` делят пять разных фич. Ошибка одной
панели всплывает в чужой плашке.

### 3.2 Clean Architecture — граница нарушена самим `ChatState`

Правило «UI знает только `ChatState`» выполняется **буквально и нарушается по сути**: сам `ChatState`
импортирует 31 тип из `data` и конструирует конкретные реализации — `LlmClient`, `LocalLlmClient`,
`LlmServiceClient`, `OllamaEmbedder`, `HashingEmbedder`, `KnowledgeIndex`, `ProjectDocsIndex`,
`CliSkillRunner`. Плюс мутирует глобальный статик `HttpProxy.url` с комментарием, который сам признаёт
хрупкость: *«ДО создания клиентов (их движки читают HttpProxy при конструировании)»* — переставь две строки,
и прокси тихо перестанет применяться.

`Main.kt` подписан «Composition root», но инжектит лишь 2 стора и 2 фабрики; остальные ~15 коллабораторов
собирает `rebuildAgent()` внутри UI-класса. Composition root'ов фактически два, и настоящий — не там,
где написано.

### 3.3 ISP/LSP — жирный порт и тихо неполная реализация

```kotlin
interface LlmGateway {
    suspend fun complete(
        messages: List<Message>,
        tools: List<Tool> = emptyList(),
        params: LlmParams = LlmParams(),
        executeTool: (suspend (String, String) -> String)? = null,
    ): GatewayResponse
}
```

Один метод упаковывает **три разных протокола**: простой запрос, тюнинг генерации и агентский tool-loop
с инверсией управления через callback. Из ~30 мест вызова `tools` передают только **3**. Из двух реализаций
tool-loop поддерживает только одна: `LocalLlmClient` молча игнорирует `tools` и `executeTool`.

**Default-параметры — это то, что делает разрыв невидимым.** `LocalLlmClient` реализует контракт
синтаксически, не реализуя семантически, и компилятор доволен. Практическое следствие: пользователь
выбирает локальную модель при включённом MCP (День 27 — «весь агент локально»), и агент **перестаёт звать
инструменты без единой ошибки** — ни компилятор, ни рантайм, ни UI не сигналят. Ответы теряют свежие данные
и официальные ссылки, то есть ровно ту планку качества, ради которой MCP и делался.

Похожая протечка у `Embedder`: в порту нет `close()`, хотя главная реализация держит HTTP-клиент — поэтому
`(emb as? OllamaEmbedder)?.close()` повторён **9 раз**. Любой третий эмбеддер с ресурсами будет молча течь.

И обратный случай — `MemoryStore`: 9 методов из двух несвязанных кластеров, при этом **ни одного потребителя
в домене**. «Доменный порт», которым пользуется только UI: политика «что и когда сохранять» живёт в
`ChatState`, поэтому не переносится в CLI/сервис и не тестируется.

### 3.4 DRY — дублирование как двигатель god-object'а

**23 копии** одного «панельного метода»: `guard-флаг → flag = true → сброс → scope.launch →
runCatchingCancellable → note → finally flag = false`. Меняются только имя флага и одна доменная строка.

Показательная деталь: комментарий «всегда: иначе спиннер залипнет» встречается **пять раз** — одну и ту же
багу лечили точечно в пяти копиях вместо одного места. При этом обобщение **уже написано** — `serviceCall`
(строки 1210–1222) — но применено лишь к 2 методам из 23.

Тройной клон RAG-эвалов (`runGoldAnswers` / `runGoldRetrieval` / `runCitationEval`) построчно идентичен.
Утечка эмбеддера при исключении вне `runCatching` воспроизведена во всех копиях — `close()` не в `finally`,
в отличие от `buildIndex`, где `finally` есть.

**Это и есть механизм роста файла:** каждая новая фича = +1 флаг, +1 note, +30 строк клона в тот же класс.

### 3.5 KISS — размеры и вложенность

`McpToolsDialog` — 208 строк с вложенностью **12 уровней**, причём внутри разметки считается regex-группировка
серверов по описаниям тулов: пересчитывается на каждой рекомпозиции и невидима для тестов.

`RagDialog` (188 строк) — «музей ченджлога»: секции «Шаг 1/2/3», «День 24», «День 28» склеены линейно.
Структура экрана повторяет хронологию разработки, а не задачи пользователя.

## 4. Что здорово — не трогать

Аудит обязан быть честным в обе стороны. Эти места — **эталон для подражания при рефакторинге**, а не
кандидаты на переделку:

- **`domain/TaskStateMachine.kt`** (136 строк) — образцовый data-driven FSM: переходы описаны **данными**
  (`TRANSITIONS`), а не ветвлениями; маленькие расширения `canTransition`/`tryTransition`.
- **`domain/Ports.kt`** (107 строк) — компактные документированные интерфейсы, корректный DIP.
- **`domain/TaskOrchestrator.kt`** — 670 строк, но **декомпозирован**: стадии по 8–46 строк, `when` по 3–5 веток.
- **`Main.kt`** (80 строк) — тонкий запуск окна.
- Мелкие вью-модели и клиенты (`McpClient` 163, `Embedders` 138, `LlmServiceClient`) — ровно нужного размера.

Целевой стиль уже существует внутри проекта. Задача — распространить его на UI-слой, а не изобретать новый.

## 5. Как это решают в индустрии

### Google (официальное руководство Android + Now in Android)

> *«Regardless of its size or scope, every UI element has a 1:1 relationship with its corresponding state holder»*
> — [developer.android.com/topic/architecture/ui-layer/stateholders](https://developer.android.com/topic/architecture/ui-layer/stateholders)

Google **прямо запрещает** глобальный state holder на всё приложение. Плюс различает два вида холдеров:
**business logic** (ViewModel — данные) и **UI logic** (обычный класс, как `NiaAppState` — что показано,
навигация). В `ChatState` они перемешаны: `mcpDialogOpen`/`interviewOpen` лежат рядом с `send()`/`advanceTask()`.

Now in Android — эталон масштаба: **6 feature-модулей** (не десятки), правило «фича зависит только от `api`
другой фичи», UDF (состояние вниз, события вверх), UI state как immutable data class или sealed-иерархия.

### Square / Cash App — Workflow

Дерево workflow, каждый владеет **своим приватным State**; родитель не хранит состояние детей, а собирает
«большие view-model из маленьких» через `renderChild`.
[square.github.io/workflow](https://square.github.io/workflow/)

### Airbnb — Mavericks

Единица состояния = **экран**: один immutable data class + один ViewModel. Ключевой приём —
**`Async<T>`** (`Uninitialized | Loading | Success | Fail`) вместо троек `isLoading + error + result`.
У нас таких троек десятки (`ragBuilding + ragNote + ragComparison`, `optRunning + optBefore + optAfter`, …) —
`Async<T>` сжимает 94 поля примерно втрое и **убирает невозможные состояния** (`loading = true` и `error != null`
одновременно). [github.com/airbnb/mavericks](https://github.com/airbnb/mavericks)

### Uber — RIBs + Plugin Points

> *«Application state is largely managed and represented by the RIBs that are currently attached to the RIB tree»*

Глобального god-state нет: **состояние = какие узлы сейчас прикреплены**. Для нас это означает `sealed class
ActivePanel { None; Rag(RagState); Mcp(McpState); … }` вместо булевых `*Open`-флагов — закрыл панель, и её
состояние умерло целиком, нечего забывать сбрасывать. Plugin Points: сотни фич интегрированы через ~50 точек
расширения, 80% кода в плагинах. [github.com/uber/RIBs](https://github.com/uber/RIBs) ·
[uber.com/blog/plugins](https://www.uber.com/us/en/blog/plugins/)

### Slack — модульность api/impl

> *«Features can link against the Interface module of other Features, but not against their Implementations»*
> — [slack.engineering](https://slack.engineering/stabilize-modularize-modernize-scaling-slacks-mobile-codebases-2/)

У нас зачаток уже есть — `domain/Ports.kt` играет роль services-api.

### Канон Мартина

- **Clean Architecture**: правило зависимостей говорит только о **направлении**, а *«the circles are schematic»* —
  число классов в адаптерном слое не догма. **Несколько state-holder'ов не нарушают Clean Architecture,
  а восстанавливают её.** [blog.cleancoder.com](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)
- **ISP**: *«Clients should not be forced to depend upon interfaces that they do not use»* → ролевые интерфейсы
  `ChatCompletion` / `ToolCallingLlm` вместо одного жирного `complete(...)`.
- **CCP** (Common Closure): *«Gather into components those classes that change for the same reasons and at the
  same times»* — даёт **объективный тест по git-истории**: поля RAG менялись вместе (Дни 21–25), локальной LLM —
  вместе (Дни 26–30). Это и есть границы разреза.
- **Ports & Adapters (Cockburn)**: порт — «целевой разговор», портов мало (2–4), делятся **по назначению,
  а не по технологии**. Валидация: `LlmGateway` с адаптерами cloud/Ollama — канонично; заводить
  `CloudLlmGateway`/`OllamaGateway` было бы ошибкой.

### Прививка от карго-культа (обязательна)

- **CUPID (Dan North)**: формальное дробление создаёт *«artificial seams»*. Резать по **domain-based purpose**,
  а не по техническому признаку. Тест качества разреза: имя нового класса доменное (`RagPanelState`),
  а не техническое (`StateManagerHelper`). [dannorth.net](https://dannorth.net/blog/cupid-for-joyful-coding/)
- **BSSN («Best Simple System for Now»)**: не закладываться на гипотетическое будущее. Дробить там,
  где боль **уже есть**; не заводить интерфейсы «на будущее», не вводить Redux/event-bus, пока нет двух
  реальных потребителей.
- **Vertical Slice (Bogard)**: *«Minimize coupling between slices, and maximize coupling in a slice»* —
  и **не вводить прослойку-делегат** между panel-state и доменом только ради слоя.

## 6. Целевая архитектура

```
Main.kt / AppComposition        ← единственный composition root: собирает граф, отдаёт порты
        │
        ├── ChatState (тонкий)  ← только ядро чата: current, input, send, диалоги
        ├── AppState (plain)    ← UI-логика: какая панель/диалог открыт (аналог NiaAppState)
        │
        └── feature-holders     ← по одному на фичу, каждый со своим scope и своими портами
              RagPanelState · McpPanelState · LocalLlmPanelState · ServicePanelState
              InterviewState · DevHelpState · AccountsState · TaskFlowState
```

Соответственно `ui/App.kt` распадается по файлу на панель: панель получает **только своё** под-состояние
и лямбды-события, а не весь god-object (это заодно чинит лишние рекомпозиции — чтение чужого
`mutableStateOf` подписывает scope на чужие изменения).

## 7. План рефакторинга

Порядок выбран по критерию «максимум эффекта на единицу риска». Каждый этап самодостаточен и оставляет
проект в рабочем состоянии.

| # | Шаг | Эффект | Риск |
|---|---|---|---|
| 0 | **Тест-опора**: детерминированный харнесс на 2–3 сценария (как `runRagCountryCheck`) | страховка для всех шагов | нет |
| 1 | **`PanelOp`** — один хелпер вместо 23 копий (`running`/`note`/`finally`) | −300 строк, чинит залипание спиннера в одном месте | низкий |
| 2 | **`Async<T>`** вместо троек `running + note + result` | ~94 поля → ~35, уходят невозможные состояния | низкий |
| 3 | **Фабрика `cioClient(json, timeouts, proxy)`** + 3 именованных `Json` | 8 мест → однострочники, таймауты перестают расходиться | низкий |
| 4 | **Вынести `rebuildAgent` в `AppComposition`** рядом с `Main.kt` | один composition root; `ChatState` получает готовые порты; чинится и класс ошибок «порядок init» | средний |
| 5 | **Резать по фичам**: `RagPanelState`, `McpPanelState`, `LocalLlmPanelState`, `ServicePanelState`, … | SRP; фича = свой файл | средний |
| 6 | **`App.kt` → файл-на-панель**, панель принимает своё под-состояние | читаемость, меньше рекомпозиций | средний |
| 7 | **Разрезать `LlmGateway`** на `ChatCompletion` + `ToolCallingLlm`; tool-loop → доменный `ToolLoopRunner` | чинит LSP-разрыв: локальная модель получает tool-loop честно | средний |
| 8 | **`Embedder.close()`** в порту | −9 даункастов, конец протечке | низкий |
| 9 | **`sealed ActivePanel`** вместо булевых `*Open` | состояние = что открыто | средний |
| 10 | **Plugin point `DevPanel`** — регистрация панелей списком | `App.kt` перестаёт расти на каждый «День NN» | средний |

Шаги 1–3 — механические и почти без риска, но снимают большую часть объёма. Начинать с них.

**Чего НЕ делать:** не разносить «все поля в один файл, все методы в другой» (рвёт common closure);
не заводить интерфейс на каждый холдер «на будущее»; не абстрагировать Compose; не вводить event-bus.

# Рефакторинг по принципам

## Порядок работы

1. **Сначала измерь, потом суди.** Никаких «выглядит плохо». Собери числа:
   строки файла; число полей состояния; число публичных функций; число зон ответственности;
   импорты между слоями; повторы одного шаблона; длина самых больших функций; максимальная вложенность.
   Каждая находка — с `file:line` и цитатой. Без доказательства находки нет.

2. **Определи акторов (SRP по Мартину).** SRP — не «класс делает одну вещь», а «одна причина изменения».
   Вопрос: *кто* и *почему* просит менять этот файл? Разные заказчики изменений → разные модули.
   Объективный тест (CCP): загляни в git-историю — что менялось вместе, то и живёт вместе.

3. **Проверь интерфейсы на ISP и LSP.**
   - Сколько клиентов используют каждый метод? Метод, нужный 3 вызовам из 30, — кандидат в отдельную роль.
   - Осторожно с default-параметрами: они **маскируют** жирный интерфейс и делают LSP-разрыв невидимым
     для компилятора. Проверь каждую реализацию: не игнорирует ли она часть контракта молча?
   - Протечка абстракции: если потребители даункастят порт до конкретного типа (например, ради `close()`) —
     чего-то не хватает в самом порту.

4. **Найди дублирование — но выбери, что схлопывать.** Ищи повторяющийся *каркас* (guard → флаг → launch →
   catch → finally). Считай копии. Если одну и ту же багу чинили в нескольких копиях — это доказательство.
   При этом: DRY служит KISS, а не наоборот. Не абстрагируй то, что просто похоже внешне.

5. **KISS и размеры.** Функция > 60 строк, вложенность > 4, вычисление данных внутри разметки —
   красные флаги. Но: длинный файл из маленьких функций — норма; проблема в длинных функциях
   и несвязанных зонах.

6. **Обязательно назови, что трогать НЕ надо.** Аудит без этого раздела — не аудит, а разнос.
   Найди в проекте места, которые уже сделаны хорошо, и объяви их эталоном стиля для рефакторинга.

## Правила разреза

- Резать по **доменному смыслу**, а не по техническому признаку. Имя нового класса доменное
  (`RagPanelState`), а не техническое (`StateManagerHelper`). Формальное дробление создаёт
  «artificial seams» (CUPID).
- Несколько адаптеров/холдеров **не нарушают** Clean Architecture: правило зависимостей — про направление,
  а число классов в слое не догма.
- Порт = «целевой разговор» (Cockburn), портов мало и делятся по назначению, **не по технологии**:
  один `LlmGateway` с адаптерами cloud/local — правильно; отдельные порты под каждого вендора — нет.
- Тройку `isLoading + error + result` заменяй одним `Async<T>` (`Uninitialized|Loading|Success|Fail`):
  меньше полей и исчезают невозможные комбинации.
- Состояние — как можно **ниже** и как можно **короче живущее**: холдер панели рождается с панелью
  и умирает с ней. Открытая панель = существующее дочернее состояние (`sealed ActivePanel`), а не булев флаг.
- Composition root ровно один. Если объекты собираются внутри presentation-класса — это второй, скрытый root.

## Ограничители (против карго-культа)

- **BSSN:** рефакторь там, где боль **уже есть**. Никаких интерфейсов, слоёв и фабрик «на будущее».
- **Не вводить прослойку-делегат** между слоями только ради слоя (Bogard).
- **Не всё под снос:** здоровые части оставить и использовать как эталон.
- Каждый шаг оставляет проект рабочим; порядок — от механического и безрискового к структурному.

2. Таблица метрик с доказательствами.
3. Нарушения по принципам: что / `file:line` / чем вредит / как чинить.
4. Что здорово — не трогать.
5. План шагами: эффект и риск на каждый, начиная с механического.

## 9. Чек-лист ревью (короткая версия скилла)

- [ ] Класс держит одну причину изменения? Кто заказчик изменений?
- [ ] Состояние живёт как можно ниже и умирает вместе со своим UI?

- [ ] Все ли реализации интерфейса честно поддерживают контракт (нет молчаливого игнора параметров)?
- [ ] Не маскируют ли default-параметры жирный интерфейс?
- [ ] Не даункастят ли потребители порт до конкретного типа?
- [ ] Повторяющийся каркас встречается более двух раз?
- [ ] Функция ≤ 60 строк, вложенность ≤ 4, в разметке нет вычислений?
- [ ] Composition root ровно один?
- [ ] Слои: `domain` без импортов `data`/`ui`/фреймворков?
