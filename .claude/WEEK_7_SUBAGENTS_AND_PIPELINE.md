## 2. Субагенты: зачем и когда

**Проблема, которую решают:** длинная сессия падает, когда **заканчивается контекст**. Идеал сервиса —
решить задачу пользователя за минимум итераций (в пределе — одна сессия / один запрос). Субагенты
растягивают жизнь сессии: у оркестратора остаётся окно **только под оркестрацию**, а тяжёлая работа
уходит в подпроцессы с собственными окнами.

**Своё vs встроенное.** Речь про **создание своих субагентов в своём коде/продукте**, а не про субагентов
Claude Code (их лектор упоминает лишь как знакомый пример — «в Claude Code они появились одними из первых»).

**Своя задача + свой контекст.** Каждый субагент решает **одну конкретную подзадачу** и имеет
**полноценное изолированное контекстное окно** (напр. Opus с 1M токенов → у каждого мелкого субагента
свой ~1M). Это резко замедляет сжатие контекста у оркестратора.

**Когда один агент, когда субагенты (слайд 15):**

| | 🟠 ОДИН АГЕНТ (простые задачи) | 🟣 СУБАГЕНТЫ (сложные задачи) |
|---|---|---|
| Объём | Одна операция | Много файлов / модулей |
| Контекст | Один контекст | Разные контексты |
| Логика | Линейная | Параллельная работа |
| Пример | «Добавь поле в модель» | «Сделай фичу авторизации» |

**Не только код.** Пример лектора — планирование поездки: один субагент подбирает билеты, другой смотрит
даты в календаре, третий изучает форумы про лучший сезон. Прямая аналогия для нашего продукта — **визовое
исследование** (см. §12).

## 3. Паттерны делегирования (слайды 17–19)

- **Fan-Out** — главный агент раздаёт задачи **параллельно** нескольким субагентам (`Main → A, B, C`).
  Так работает почти любой кодовый ассистент. Параллель сокращает время в **2–4, иногда 10 раз**.
- **Chain** — **последовательная** передача результата (`A → B → C`): выполнился первый, потом второй…
- **Router** — **маршрутизация по условию**: по условию запускается тот или иной агент (`Code / Docs / Test`).

Реальные ассистенты умеют **все три сразу**, и оркеструет их **один главный поток**.

**Реальный пример (слайды 20–21):** `claude --agent refactor-mobile` запускает 2 параллельных субагента:
- `builder-spring-feature` (Build Spring backend) — Done · 51 tool uses · 96.2k токенов · 7m 59s
- `builder-compose-feature` (Build Compose UI) — Done · 69 tool uses · 97.2k токенов · 9m 3s
- Итог: **~17 минут вместо ~35, экономия 50%** (backend + frontend одновременно, отдельные тулзы/токены/время).

## 4. Коммуникация Main↔Sub и жизненный цикл (слайды 21, 25)

**Контракт обмена:**

| Направление | Что передаётся |
|---|---|
| **Контекст ↓** (Main → Sub) | задача · файлы/пути · ограничения |
| **Результат ↑** (Sub → Main) | статус (ok/fail) · изменённые файлы · логи/diff |
| **Ошибки ⚠** (обрабатывает Main) | retry · fallback · отмена |

Всё это **детерминированно кодится** — получите полноценную работу с кучей агентов, адаптированных под
вашу задачу (не только код: тревел-агент, авто-подбор, поиск объявлений и т.п.).

**Жизненный цикл субагента:** `SPAWN` (Main создаёт с контекстом) → `EXECUTE` (работа над задачей) →
`REPORT` (возврат результата) → `MERGE` (Main объединяет изменения) → субагент умирает.

## 5. System Tooling (слайды 26–35)

**Три категории инструментов агента (слайд 29):**
1. **RAG Tools** — Ollama, векторизация документов и т.п. (уже есть у нас: неделя 5).
2. **MCP Tools** — MCP-серверы (GitHub, Postman…) (уже есть: неделя 4).
3. **System Tools** — find files, bash-команды, запуск приложений, работа с файлами.

Любой современный ассистент содержит **комбинацию этих трёх**, выбирая нужное по промпту и своим MD-файлам.

**Единый интерфейс тула (слайд 31):**
```kotlin
interface Tool {
    val name: String            // для LLM: как называется
    val description: String     // для LLM: что и зачем вызывать
    val parameters: List<ToolParameter>  // валидация входа
    suspend fun execute(ctx: ToolContext): ToolResult  // логика
}
// Каждый тул = отдельный класс. name+description — для LLM, parameters — валидация, execute — логика.
```

**Исполнение (слайды 32–33):** `ToolExecutor` держит `ToolRegistry`, находит тул по имени
(`registry.findByName(call.name)`), вызывает его `execute` в `ToolContext`, возвращает `ToolResult`.
`ToolRegistry` — регистрирует инструменты. Это упрощённая модель того, как работает Claude Code.

**Tool Selection / Function Calling (слайды 34–36):**
```
User Request → LLM Analyze → Tool Selection → Call execute() → Result → LLM → User Response
```
- **Function Calling** — LLM получает список tools + descriptions (кладём в систем-промпт) и выбирает
  нужный **по смыслу запроса** (матчит по словам: «прочитай папку» → тул «чтение файла»).
- **Tool Use Loop** — LLM может вызвать **несколько** тулов последовательно/параллельно (прочитать файл +
  сравнить с другим + дёрнуть MCP GitHub), результаты собираются и возвращаются в LLM, та решает, что
  отдать юзеру.

## 7. AI Pipeline (слайды 39) и пример Дня 32 (слайды 40–41)

**Общая форма пайплайна:**
```
TRIGGER            INPUT              AGENT                 OUTPUT              ✅
(PR / расписание / (diff / docs /     (RAG + LLM + Tools)   (review / file /
 событие / query)   data)                                   msg / deploy)
```
Пример из речи: триггер — залил APK в Store / прилетела SMS; агент через **MCP Chrome** заполняет поля в
Apple/Google Store и деплоит — «а мы в этот момент пьём кофе».

**Пример «День 32 — автоматизация ревью кода» (GitHub Actions + AI):**
```
PR Created → Get DIFF → RAG: Docs → LLM Review → Post Comment
```
1. Создаётся PR → берём **diff** (это Input Data).
2. Из **RAG** достаём документацию: как должен быть оформлен PR, что должно/не должно быть.
3. **LLM ревьюит** PR с подключёнными доками через RAG.
4. Пишет **комментарий** («не рекомендую по таким-то причинам / такие-то ошибки»), при наличии прав может
   **заблокировать merge**.

Реализация — простой GitHub workflow, скрипт на Python (или любом языке), запускается на каждый PR:
```yaml
# .github/workflows/ai-review.yml
on:
  pull_request:
    types: [opened, synchronize]
jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python ai_review.py --diff ${{ github.event.pull_request.diff_url }}
```

## 8. Error Handling (слайды 42–44)

Идеальная инфраструктура должна работать надёжно, а AI **априори ненадёжен** → нельзя ломать пайплайн и
пушить «не то».

| Стратегия | Когда | Что делаем |
|---|---|---|
| **Retry** | LLM упала / вернула мусор / тайм-аут / rate limit | Повторный запрос с другим промптом, возможно к другой модели; прогрессивная сетка; **макс. 3 попытки**. |
| **Fallback** | Retry не помог | Альтернативная стратегия: другая модель, упрощённый промпт, дефолтный ответ, детерминированная проверка (линтеры), уведомление человеку. **Стратегия, а не проглоченный лог.** |
| **Human-in-the-Loop** | Опасная операция / критическое решение / агент не уверен / платёжная система | Подключаем человека (Slack/SMS дежурному), approval workflow. |

**Правило:** сервис **никогда не полностью автоматический**. Долю участия человека можно снижать со
временем, но точки подключения должны оставаться.

## 9. Pipeline Metrics (слайд 45)

| Метрика | Что меряем | Ориентир-цель (со слайда) |
|---|---|---|
| **Latency** | Время от триггера до результата, перцентили P50/P95/P99. Бейзлайн — среднее по последним 10–30 прогонам. | **< 60s** для review |
| **Cost** | Стоимость одного прогона = токены × цена модели. Алерт, если PR вдруг стал в 2× дороже. | **< $0.10** за PR |
| **Quality** | Точность и полезность = golden set + human eval (люди ставят оценки). | **> 60%** полезных (в речи — цель ~80% «выше восьмёрки»/пальцев вверх) |
| **Reliability** | Процент успешных прогонов без ошибок и fallback. | **> 95%** uptime |

Без **quality-gate** запускать AI бессмысленно («AI ради AI»). Метрики динамические — система меняется,
их надо пересматривать.

## 10. Pipeline Testing (слайд 46)

| Тест | Суть |
|---|---|
| **Golden Set** | 10–20 эталонных примеров (напр. старые PR с известными багами) + ожидаемые комментарии. Прогоняем, сравниваем, тюним промпт до схождения. Regression после изменения промпта. Можно автоматизировать той же нейронкой. |
| **A/B Testing** | Сравнение версий: Prompt v1 vs v2, Model A vs Model B. Метрика — % полезных комментариев. |
| **Smoke Test** | Быстрая проверка перед каждым деплоем: pipeline запускается, вывод не пустой, формат корректный, комментарии валидны (не бред, соответствуют контексту). |
| **Human Eval** | Периодически человек оценивает output (👍/👎), feedback loop → правка промпта. Никогда не отмирает. |

- Поймать **реальные трудности интеграции** — когда собираешь MCP+RAG+память+локаль вместе, всплывают
  косяки, у каждого свои. Задача — поймать их и научиться разбираться → к концу челленджа выйти
  «боеготовой единицей».
- Наконец-то есть **время на архитектуру и рефакторинг** — чтобы «красиво выглядело, не отъедало гигабайты
  оперативы на старте», а не «АБК-как-нибудь работало».
- Выйти **чуть дальше демо-образцов** — с реальным продуктом, а не Hello World. В прошлых потоках люди
  выпускали приложения в Apple Store / Play Market, которые даже приносят деньги.
- **В конце недели — второе, прощальное видео** (подытоживающее: как жить с этими знаниями дальше).
