## 0. TL;DR недели

- **Local LLM = генеративная модель, работающая ПОЛНОСТЬЮ на локальном устройстве** (ПК, сервер,
  Raspberry Pi, смартфон). Неделя 5 гоняла локально только **эмбеддер** (nomic-embed-text); неделя 6 —
  запускаем локально **саму отвечающую LLM** (llama3.2 / qwen2.5 и т.п.) вместо облачной DeepSeek/OpenRouter.
- **Зачем локально:** ① **цена** — облако платит за токены (5–20$ / 1M токенов) бесконечно, локаль = железо
  один раз (окупается за пару лет при реальном кодинге); ② **приватность** — данные не покидают машину,
  можно вообще выдернуть интернет; ③ **автономность** — не зависишь от Wi-Fi/白-списков/лимитов; ④
  **масштабируемость** — «заплатил один раз», сложно перегрузить свой Mac mini.
- **Как это возможно на домашнем железе — КВАНТИЗАЦИЯ.** Веса модели (кучка тензоров, FP16 = 2 байта/число)
  «сжимаются» в менее точный формат (FP16→INT8→INT4). 8B-модель: FP16 ≈ 16 GB VRAM, Q4 ≈ 4 GB VRAM.
  Платим лёгкой потерей качества, взамен — влезает в бытовую видеокарту/ноутбук.
- **Локальная маленькая модель уступает облаку на сложном, но для многих задач 7B хватает.** Бенчмарк:
  Llama 3.1 8B (MMLU 69.4%) вплотную к GPT-3.5 (71.4%); Phi-3 Mini 3.8B (68.8%) обгоняет модели крупнее.
- **Инструменты запуска:** **Ollama** (проще всего, CLI+API — наш выбор, уже стоит), llama.cpp (гибкость +
  мобилки), LM Studio (GUI для новичков), MLX (Apple Silicon), vLLM (серверы).
- **Local LLM + RAG — мастхэв** (прямая цитата лектора). Локальная модель отстаёт от жизни (open-source
  релизы с лагом 3–12 мес) и склонна галлюцинировать → RAG обновляет знания и привязывает ответ к чанкам.
- **ДЗ недели (слайд GOALS):** ① установить локальную LLM · ② поработать с ней · ③ **сравнить локальную и
  облачную LLM**. Практический ориентир лектора: **тумблер cloud ↔ local + сравнение двух ответов**,
  прогнать через локаль все «джедайские техники» (MCP, RAG, task-state), маркировать, чей ответ.
- Организационное: **следующая (7-я) неделя — практически последняя, и там будет ДВА видео**.

## 1. Конспект лекции (что усвоить перед кодом)

| Тема | Суть |
|---|---|
| **Что такое Local LLM** | Модель, крутящаяся целиком на локальном устройстве. Облачные нейронки — те же LLM, просто развёрнутые в чужих дата-центрах. |
| **Что не так с облаком** | **Дорого** (платишь за токены вечно), **нет приватности**, **зависимость от интернета**, **не масштабируется** (больше юзаешь — больше платишь). Локаль обратна по всем пунктам. |

| **Как устроена LLM** | Огромный набор **весов** в слоях. Input layer → Hidden layers (self-attention/трансформеры) → Output layer. **Forward** = предсказание, **Backward** = обучение (правка весов). |
| **Термины** | **Weight** (числовое значение связи нейронов), **Node** (нейрон), **Layer** (группа нейронов), **Output** (взвешенная сумма входов). |
| **Параметры** | «B» в `Llama 70B`, `Qwen 3.5B` = миллиарды **параметров** = кучка тензоров. FP16 → 2 байта/параметр. 8B × 2 байта ≈ **16 GB** (должно влезть в видеопамять). |
| **Больше параметров** | → медленнее инференс → больше памяти → **выше качество**. Компромисс. |
| **Ограничения локали** | **Скорость** (бытовая GPU ≠ серверный кластер) и **качество** (3–8B уступают GPT-4o на сложном). Но для многих задач 7B достаточно. |
| **Квантизация** | Разбиение множества весов на менее точное по алгоритму: FP32→FP16→INT8→INT4. Меньше памяти/ресурсов ценой лёгкой потери точности. **Главный ключ к запуску дома.** |
| **Форматы Q** | `Q8_0`/`Q6_K`/`Q5_K_M`/`Q4_K_M`/`Q4_K_S`/`Q3`/`FP16` — trade-off качество/скорость/железо. Выбор — под конкретную модель, экспериментально. |
| **Почему облако мощнее** | **Динамич. параметризация** (простой вопрос → маленькая модель), **MoE / гибридная архитектура** (Multi-Experts), **Dataset Quality** (разметка/файнтюнинг), Active 20–60B / Total 200–1000B параметров. |
| **Tooling** | Ollama, llama.cpp, LM Studio, MLX, vLLM. Совет: попробовать все, сделать простой бенчмарк, выбрать по ощущению. |
| **Мобилки** | GGUF до ~3B: iOS (llama.cpp/MLX/Core ML), Android (llama.cpp/MediaPipe/MLC). iPhone 15 Pro тянет Llama 3.2 1B; Snapdragon 8 Gen 3 — Phi-3 Mini. |
| **Применение** | Оффлайн-ассистент, суммаризация, автодополнение кода (без утечки на сервер), внутренний чат-бот, классификация. |
| **RAG + Local LLM** | Развернул локальную LLM — грех не развернуть локальный эмбеддер. RAG лечит устаревшие знания и галлюцинации. |

## 2. Экономика: Cloud (API) vs Local (слайд 04)

| | ☁️ CLOUD (API) | 💻 LOCAL |
|---|---|---|
| Цена | 5–20$ за 1M токенов (**платишь вечно**) | стоимость железа (**один раз**) |

| Масштаб | не масштабируется (плати за токены) | масштабируемо (заплатил однажды) |

## 3. Как устроена LLM (слайды 05–09) — фундамент под квантизацию

```
Input Layer  →  Hidden Layers (1..N, self-attention/трансформеры)  →  Output Layer
   ↑ forward propagation = предсказание
   ↓ backward propagation = обучение (правка весов)
```
- **Параметры = кучка тензоров.** Пример тензора (FP16):
  ```
  W_fp16 = [ [ 0.12, -0.35,  0.52, -0.08 ],
             [ 0.01,  0.27, -0.52,  0.45 ] ]
  FP16 = Float16 → каждое число 16 бит (2 байта)
  ```
- **Размер модели ≈ параметры × байт/параметр.** 8B × 2 байта (FP16) ≈ **16 GB**; 70B ≈ 140 GB.
  Чем больше параметров — тем больше видеопамяти нужно (у Mac mini выигрыш — unified memory).

**Таблица размеров (слайд 11):**

| Модель | Параметры | FP16 | Q4_GGUF | Железо |
|---|---|---|---|---|
| 1B | 1 млрд | ~2 GB | ~0.5 GB | любой ноутбук, CPU |
| 3B | 3 млрд | ~6 GB | ~1.2 GB | CPU / встроенная GPU |
| 7B | 7 млрд | ~14 GB | ~3.5 GB | GPU 6–8 GB VRAM (RTX 2060/3050/4060) |
| 13B | 13 млрд | ~26 GB | ~7 GB | GPU 12–16 GB VRAM (3060/4070Ti) |
| 30B | 30 млрд | ~60 GB | ~15 GB | GPU 24–48 GB VRAM (3090/4090/A6000) |
| 70B | 70 млрд | ~140 GB | ~35–40 GB | мульти-GPU или H100/A100 |
| 400B | 410 млрд | ~820 GB | нет смысла дома | HPC-кластеры, 8+ GPU |

**Ограничения (слайд 14):** *Скорость* — локаль медленнее из-за железа; *Качество* — 3–8B уступают GPT-4o
на сложном, но для многих задач 7B хватает.

**Бенчмарк (слайд 15):**

## 4. Квантизация (слайды 16–22) — как влезть в домашнее железо

**Определение:** разбиение существующего множества весов на **менее мощное** множество по алгоритму.
```
FP32 (32 bit) → FP16 (16 bit) → INT8 (8 bit) → INT4 (4 bit)
```
Чем сильнее сжали — тем меньше памяти/ресурсов, тем эффективнее (ценой лёгкой потери точности).

**Математика квантизации (слайд 19), пример FP16 → INT8:**
```
max_abs = |0.52| = 0.52                 # макс. модуль в тензоре
Q_MAX   = 127          (для int8)
scale   = max_abs / Q_MAX = 0.52 / 127 = 0.004094
q = round(w / scale):
   0.31 / 0.004094 =  75.7  ->  76
  -0.27 / 0.004094 = -65.9  -> -66
   0.52 / 0.004094 =  127   ->  127
  -0.52 / 0.004094 = -127   -> -127
```
Информация чуть теряется, но множество «сжимается» (несколько значений прячутся в одном).

**Пример по моделям (слайд 20):**

| Модель | До квантизации | После | Формат |
|---|---|---|---|
| LLaMA 2 7B | 6.7B / 13.4 GB / 16 bit | 3.8 GB | Q3 (3.5 bit) |
| Qwen 2.5 7B | 7B / 14 GB / 16 bit | 3.3 GB | Q4_K_S (4 bit) |
| LLaMA 3 8B | 8B / 16 GB / 16 bit | 8.6 GB | Q8_0 (8 bit) |

> **LLaMA 3 8B: FP16 = 16 GB диск / 16 GB VRAM → Q4 = 3.5 GB диск / ~4 GB VRAM.**

**Форматы GGUF (слайд 22) — что выбирать:**

| Формат | Биты | Качество | Скорость | Где использовать |
|---|---|---|---|---|
| Q8_0 | 8 | средняя | средняя | когда важна точность |
| Q6_K | 6 | ~FP16 | хорошая | хороший баланс |
| **Q5_K_M** | 5 | **лучший баланс** | быстрее | для большинства |
| **Q4_K_M** | 4 | чуть хуже | быстрый | **идеально на ноутбуке** |
| Q4_K_S | 4 | заметно хуже | быстрее всех | слабые CPU |
| Q3 | 3 | заметно хуже | оч. быстрый | эксперименты |
| FP16 | 16 | идеал | медленно | только мощные GPU |

> `Q<n>` = во сколько раз ужимаем. Trade-off **специфичен для модели** — брать конкретную (Qwen/Llama),
> экспериментировать или читать чужие отчёты. Даже «хорошая» модель галлюцинирует → жёстко строить flow
> (как на неделе памяти) и подпирать RAG-ом.

## 5. Почему облако всё же мощнее (слайды 23–24, ChatGPT 5.1)

Несмотря на дата-центры, у облака куча оптимизаций:
- **Динамическое параметризирование** — простой вопрос не гоняет триллион параметров, отдаётся достаточно
  квантированная модель.
- **Гибридная архитектура (Multi-Experts / Mix of Capabilities)** — несколько заточенных моделей (MoE) →
  ускорение, меньше токенов, меньше нагрузка на инфраструктуру/электричество.
- **Dataset Quality** — разметка данных, файнтюнинг, постоянные эксперименты (у OpenAI и т.п.).
- **Active Parameters 20–60B** (на запрос) / **Total Parameters 200–1000B** (до триллиона — для сложного:
  медицина, спецзадачи).

## 7. Применение (слайды 32–37) + RAG (38–41)

**5 сценариев Local LLM in practice:** ① оффлайн-ассистент (мобильное приложение с локальным AI) ·
② суммаризация (локальная обработка документов) · ③ автодополнение (код без отправки на сервер) ·
④ чат-бот (для внутренних корп-систем) · ⑤ классификация (предварительная фильтрация данных).

**RAG + Local LLM (пайплайн, слайд 41):**
```
Документы → Embeddings → Векторная БД
Запрос → Поиск → (Контекст + LLM) → Ответ
```
Что даёт: **устаревшие знания** — RAG обновляет контекст (open-source модели с лагом релизов); **галлюцинации**
— ответ привязан к чанкам документов; **контекст** — расширяет знания модели. Лектор: с локальной LLM RAG —
**обязателен**.

## 8. Что это значит для «Визового специалиста» (наш проект)

Ложится идеально — у нас уже есть и облачный gateway, и локальный Ollama (для эмбеддингов), и все «джедайские
техники» (MCP, RAG, task-state):

- **Локальный генеративный gateway — ✅ СДЕЛАНО (День 26).** Облачный `data/LlmClient` (Ktor) ходит в облако
  (DeepSeek/OpenRouter); рядом появился `data/LocalLlmClient` — та же реализация порта `LlmGateway`, но по HTTP
  на **`localhost:11434`**, нативный Ollama `POST /api/chat` (`{model, messages, stream:false}`), **без прокси**
  (переиспользован паттерн `OllamaEmbedder`). Дефолт — `qwen2.5:7b`.
- **Тумблер cloud ↔ local (ДЗ ③).** У нас уже есть выбор модели снизу (стиль Claude Code) и `ConfigStore` —
  добавляем «провайдера» LLM (cloud/local) + выбор локальной модели (`llama3.2:3b`, `qwen2.5:7b`, …). Всё
  остальное (MCP/RAG/CaseFile/стратегии контекста) работает поверх без изменений — меняется только gateway.
- **Режим сравнения (ДЗ ③).** Как лектор советует: один и тот же запрос → **два ответа (облако vs локаль)
  рядом**, с маркировкой чей это ответ (и, по нашей планке — с источниками RAG/MCP у обоих). Хорошо ложится
  на уже существующую RAG-панель «оба режима» с Дня 22.
- **RAG обязателен с локалью.** Держим планку [[mcp-answer-quality-bar]]: маленькая локальная модель слабее и
  галлюцинирует → грунтуем её RAG-ом (наша база) + MCP `get_visa_requirements` (живые офиц. ссылки). Это ровно
  то, что советует лекция.
- **Приятный бонус для проверки:** облачный LLM из headless-gradle **не резолвится (DNS)** — e2e гоняем только
  в GUI. А **локальный Ollama на `localhost` в headless РАБОТАЕТ** (как эмбеддер на неделе 5) → части с локальной
  LLM реально проверяемы verify-харнессом, а не только руками в GUI.
- **Грабли, которые учитываем:** (a) tool-calling (MCP) у локальных моделей поддержан не везде и капризен на
  сильно квантованных — проверить, что выбранная модель умеет функции (llama3.2/qwen2.5 умеют), иначе MCP-стадии
  деградируют; (b) [[kotlin-regex-cyrillic-trap]] — любой новый парсинг ответа писать сразу с `\p{L}`/`(?U)`;
  (c) [[corp-network-gradle-dns]] — «host unknown» это DNS, не код; локаль этим не страдает (localhost).
- **Стек совпадает:** Kotlin/JVM + Ktor к `localhost:11434`, Clean Architecture (порт `LlmGateway`, адаптер в
  `data/`, UI знает только `ChatState`). Ollama у пользователя уже установлена.
