# Промпт-инжиниринг

Суть: роль + цель + ограничения + формат + примеры сужают «бесконечный» контекст и поднимают
качество. Промпт агента — не один блок, а **слоёная система**: стабильная база + оркестр + узкие
ролевые промпты стадий. Правки вести по слоям, а не одной простынёй.

## Слои (что инжектится и в каком порядке)

Каждый запрос к стадии собирается в `TaskOrchestrator.call()`:

```
VISA_SYSTEM_PROMPT (база) → дата → CONDUCTOR (общие правила оркестра) → ролевой промпт стадии
→ [ПЕРСОНАЛИЗАЦИЯ] → [STATE] (+ [ДОСЬЕ], [СПРАВКА ПО ВИЗЕ]) → [БАЗА ЗНАНИЙ] (RAG)
→ [ЖЁСТКИЕ ПРАВИЛА] → профиль
```

Free-chat (`VisaAgent` / `ContextAssembler`) берёт только базу + слои памяти — без `[STATE]`, ролей
и RAG. Поэтому база написана с оговорками «если есть блок …», чтобы корректно работать и без них.

## Где какое правило живёт (единый источник — для НЕ-хрупких правил)

- **Личность, достоверность/источники, формат `[checklist]`, тон, анти-примеры, приоритет правил**
  → `VISA_SYSTEM_PROMPT` (`domain/VisaAgent.kt`). Каноничен; desktop ведущий, Android — форк.
- **Общие правила всех ролей** (прячь служебное; приоритет `[СПРАВКА]`; RAG-цитаты `[S1]`; делай
  только свою роль) → `CONDUCTOR` (`domain/TaskOrchestrator.kt`).
- **Поведение стадии** → ролевые const в `TaskOrchestrator`: `INTERVIEWER`, `PLANNER_OPTIONS`,
  `PLANNER_PLAN`, `EXECUTOR`, `VALIDATOR`, `ASSISTANT`.
- **3 жёстких инварианта** (legal-only / no-guarantee / scope-visa) → `BUILT_IN_INVARIANTS`
  (`domain/Invariant.kt`), инжектятся блоком `[ЖЁСТКИЕ ПРАВИЛА]` и в задачи, и в free-chat.
- **Переписывание при срабатывании стража** → `guardReprompt()` (`domain/InvariantGuard.kt`),
  общий для `VisaAgent.ask` и `TaskOrchestrator.guardFix` (раньше был дубль с расхождением).

## Load-bearing дубли — НЕ де-дуплицировать

Часть правил намеренно повторена в нескольких ролях. Это **усиление хрупкого поведения**, а не мусор,
и вычищать ради DRY нельзя — будет регресс:

- «цитируй официальные URL» (в `CONDUCTOR` + `INTERVIEWER` + `EXECUTOR` + `ASSISTANT` + заголовке
  `[СПРАВКА]`) — планка «живые ссылки на КАЖДОЙ стадии»; без усиления модель роняет ссылки.
- анти-смешение профиля (`call()` + `INTERVIEWER` + `ContextAssembler`) — против протечки профиля
  в факты кейса.
- русский пин (`LOCAL_LLM_SYSTEM`, `OPT_TASK_PROMPT`, `RAG_SYSTEM`, MCP-промпты) — разные модели/
  сервисы (локальная qwen дрейфила на китайский).

Правило: единый источник обязателен для НЕ-хрупких правил (формат, guardReprompt); для хрупких
бизнес-критичных — усиливать там, где модель их роняет, но следить, чтобы формулировки не
противоречили друг другу.

## Контракт `[checklist]`

Формат задан в `VISA_SYSTEM_PROMPT`, повторно напоминается в `EXECUTOR`, enforced кодом
(`reconcileChecklist` в `TaskOrchestrator`). Статусы только: `нужен` / `загружен` / `проверен`.
Агент ВСЕГДА пишет «нужен»; «загружен»/«проверен» ставит только система по факту приложенного файла
(раздел «Документы» в `[STATE]`). Пустой `[checklist]` и пункты «ради галочки» запрещены.
UI парсит `[checklist]…[/checklist]` (`ui/App.kt → parseSegments → ChecklistView`) в карточку со
статусами и цветами (`StatusColors`): нужен · загружен · проверен · не хватает.

## Валидация промптов

`./gradlew.bat runAgentProbe --offline` — харнесс `cli/AgentProbeMain.kt`: 12 кейсов через реальную
модель (по умолчанию облако deepseek), транскрипты в `build/agent-audit/run-*`. Прогон ~18–20 мин.
Что проверять после правок промптов: инвариант статусов `[checklist]` (все `нужен`), KPI официальных
ссылок в `EXECUTOR`, твёрдость стражей, дисциплину INTAKE (доспрашивает, не выдумывает даты),
корректность `VALIDATOR` (нет доков ≠ revise; пустой шаг = revise).
