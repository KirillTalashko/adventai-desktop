# Рефакторинг и модуляризация: платформо-осознанный скилл

> Каноничный источник (в git). Локальную установку — в `.claude/skills/refactor-architecture/SKILL.md`.
> Прикладной пример на этом проекте — [MODULARIZATION.md](MODULARIZATION.md) и [ARCHITECTURE_AUDIT.md](ARCHITECTURE_AUDIT.md).

## Установка

Ставится как локальный Claude Code skill. Каталог `.claude/skills/` — в `.gitignore` (там же `find-skills`), поэтому
в репозиторий идёт **только этот источник**, а установка — одной командой из корня проекта:

```bash
mkdir -p .claude/skills/refactor-architecture && cp .claude/REFACTOR_SKILL.md .claude/skills/refactor-architecture/SKILL.md
```

После этого Claude Code видит скилл как `refactor-architecture` и подхватывает его по `description` из frontmatter.
В приложении AdventAI факт установки отражён в диалоге **«Коннекторы агента» → Скиллы** — рядом с «Skill — документы»
и «Skill — автоулучшение промтов» (итого 3 скилла).

Скилл превращает расплывчатое «тут плохо» в **доказанную, упорядоченную, измеримую** цепочку правок,
одинаково работающую на любом стеке. Пять стадий, всегда по порядку:

```
−1. НАВИГАЦИЯ (index-first)   0. ИЗМЕРЬ   1. ПЛАТФОРМА   2. ЦЕПОЧКА (Mikado)   3. СЖАТЬ   4. МОДУЛЯРИЗИРУЙ
```

## Навигация (index-first) — сквозной протокол, ДО и во время всех стадий

**Никогда не читай большой файл целиком, если нужен один символ.** Сначала карта, потом тело. Правило — для
главного цикла И для КАЖДОГО субагента роя: иначе рефакторинг жжёт токены на чтение вместо мышления.

Порядок (карта прежде тела):
1. `map` / `large` — что вообще трогаем (крупные файлы сверху).
2. `outline <file>` — скелет: символы + диапазоны строк (для Стадии 0 «Измерь» и Mikado-разведки).
3. `usages <symbol>` / `symbol <name>` — кто зовёт / где объявлено (**ключ к Mikado**: связи прежде границ).
4. `unfold <symbol>` — тело РОВНО того, что переносишь/правишь.
5. `read` целиком — **только как последнее средство**: когда правка зависит от окружения (импорты, соседние
   строки, порядок init — как init-order NPE, который картой не поймать).

**Бэкенд навигации — свой на каждый стек, протокол один** (детектится на Стадии 1):

| Стек | Инструмент навигации |
|---|---|
| Kotlin/JVM, Android | `ast-index` репо (`outline`/`symbol`/`usages`/`map`), иначе **`kotlin-outline`** (портируемый, чистый Python stdlib) |
| Python | `ast-outline` (stdlib `ast` — точный) |
| JS/TS | tree-sitter / `smart-explore` / LSP document-symbols; `knip`/`ts-prune` для мёртвого кода |
| Прочее | document-symbols из language server, выгрузка ctags |

**Что даёт и чего НЕ даёт (честно):**
- Экономит токены на **ЧТЕНИИ** (~85% на крупных файлах: карта ≈ 10–15% объёма) → за тот же бюджет **больше
  агентов роя** или **шире охват** (весь god-object разом, а не по кускам).
- НЕ экономит на **рассуждении** (workflow-анализ, критик) — там думают, а не читают.
- Эвристические outline'ы (`kotlin-outline`) ~90% точны: многострочные raw-строки / сложные `${}`-шаблоны могут
  дать неточный конец → `unfold` + короткая сверка глазами, когда правка тонкая.

## Стадия 0 — Измерь (никаких «выглядит плохо»)

Каждая находка — с `file:line` и цитатой. Сначала числа, потом суждение. Сними baseline и держи его в `baseline.json`:

- размер: LOC по слоям/файлам; самые длинные функции; максимальная вложенность;
- состояние: число полей состояния в самом крупном классе (god-object детектится тут);
- дублирование: клоны — **PMD CPD** (JVM), **jscpd** (JS/TS), порог ~75 токенов;
- смелы: **detekt** (Kotlin), **ktlint**, **ESLint**, **PMD** — `LargeClass`/`LongMethod`/`TooManyFunctions`;
- границы: импорты между слоями (кто тянет инфраструктуру в UI/домен);
- **change-coupling: `git log --name-only`** — что меняется вместе (объективный тест общей причины изменения, CCP).

Каждый последующий PR обязан двигать эти числа **вниз**. Это и есть защита от разбухания.

## Стадия 1 — Определи платформу (ядро скилла)

Скилл читает манифесты сборки и зависимости и **сам** выбирает целевую архитектуру. Правило разрешения
конфликтов: **специфичный сигнал бьёт общий** (electron ⟶ побеждает react; android ⟶ побеждает generic-jvm).
Для монорепо детектор возвращает **несколько** платформ, а не одну.

| Платформа | Сигналы репозитория | Целевая архитектура | Форма модулей |
|---|---|---|---|
| **Desktop-JVM (Compose / JavaFX / Swing)** | `build.gradle(.kts)` + `org.jetbrains.compose` **или** `javafx.*`/`javax.swing` в исходниках; НЕТ `android.*`, web/wasm | ручной DI-корень в `:app` + `:core:domain/:core:data` + `:ui:kit` + фичи; серверные части — `:service:*` | Gradle multi-module «слой×фича» (NiA), convention plugins, **без Hilt/api-impl** |
| **Desktop (Electron/Tauri)** | `package.json` + `electron` **или** `@tauri-apps/*` в deps | процесс main/renderer (Electron) или core/webview (Tauri) — **НЕ** просто FSD | пакеты монорепо; native-слой отдельно от UI |
| **Web-SPA** | `package.json` + react/vue/svelte/angular + бандлер (vite/webpack); **нет** electron/tauri | Feature-Sliced Design (`app→pages→widgets→features→entities→shared`) **или** Nx tagged libs | FSD-слои со Steiger/dependency-cruiser-гейтом, либо Nx-пакеты |
| **iOS** | `Package.swift` / `*.xcodeproj` / `Info.plist` / `*.swift` | модульный монолит на локальных SPM-пакетах (`Core/Networking/DesignSystem/Feature-*`) | локальные SPM-пакеты; Tuist при множестве таргетов; TCA-scope для больших reducer'ов |
| **Android** | `AndroidManifest.xml` + `android.*` (+ Compose/Views) | NiA-раскладка `:app`/`:feature:*`/`:core:*` (`model/data/domain/designsystem/ui/network`) | Gradle multi-module, convention plugins + version catalog, Hilt, api/impl при боли сборки |
| **Backend-JVM** | `pom.xml`/`build.gradle` + spring-boot/micronaut/quarkus; **нет** UI-фреймворка | гексагон (порты по назначению + адаптеры) внутри bounded contexts; модульный монолит | модули = top-level пакеты (`@ApplicationModule`), ArchUnit + `Modulith.verify()` в CI |
| **Flutter** | `pubspec.yaml` + `lib/*.dart` | feature-first Dart-пакеты (`feature_*/common_ui/core`) в монорепо | Dart-пакеты под Melos / pub workspaces (Dart 3.6+) |
| **Library / CLI** | нет **ни одного** UI-тулкита (Compose/JavaFX/Swing/web) **и** нет server-стека | `:api` + `:core` **без** app-слоя; публичная поверхность минимальна | пакет/модуль по назначению, семвер публичного API |
| **KMP / Multiplatform-shared** | `commonMain`/`kotlin { targets }` | общий `:shared:core` + per-target тонкие модули | `expect/actual`, common-first |

**Инварианты, общие для ВСЕХ платформ** (не зависят от языка):
- зависимости строго вниз, циклов нет; проверяется машиной, не глазами;
- фича не зависит от фичи напрямую — общий тип едет вниз в core, или общение через api/навигацию;
- домен/ядро — ноль зависимостей от фреймворков и IO;
- composition root ровно один — только в app-слое; UI/держатель состояния не конструирует клиентов/IO.

## Стадия 2 — Построй цепочку (Mikado Method = «логические цепочки»)

Не планируй умозрительно. Строй граф пред-условий итеративно:

```
1. Попробуй целевое изменение (вынести X).
2. Смотри, ЧТО ломается компилятором/тестами.
3. Запиши сломанное как ПРЕД-УСЛОВИЕ (ребро графа) — НЕ чини на месте.
4. Откати всё.
5. Рекурсивно реши пред-условия. ЛИСТ графа (ничего не ломает) = безопасный первый шаг.
```

Листья делаются немедленно; к корню идёшь снизу вверх. Границы модулей при этом **обнаруживаются по швам**
(change-coupling из стадии 0), а не назначаются схемой слоёв — иначе получаются «artificial seams» (CUPID),
которые придётся перерезать.

**Перед движением — сеть безопасности:** характеризующие тесты (Feathers), фиксирующие ТЕКУЩЕЕ поведение
ключевых сценариев (не «правильное»). Двигать god-object без тестов = гарантированная тихая регрессия.

Инструменты извлечения: **Branch by Abstraction** (порт над тем, что меняешь → переключить потребителей →
заменить за абстракцией → убрать), **Strangler Fig** (новое растёт вокруг старого, старое усыхает),
**Preparatory Refactoring** Бека («сделай изменение лёгким, потом сделай лёгкое изменение»).

## Стадия 3 — Сжать ДО модуляризации (иначе раздувание фиксируется за границей)

Порядок «subtract-first»: убей дублирование и мёртвый код, стяни константы — и лишь потом проводи границу.

| Приём | Что сжимает | Ограничитель |
|---|---|---|
| **Дизайн-токены из одного источника** | magic numbers → семантическая шкала (`Space`/`Radii`); дубли палитры → единый источник + алиасы | одноразовые layout-числа в шкалу не тащить; Style Dictionary/`tokens.json` — только при мульти-платформенной/бренд-выдаче |
| **Строки в ресурсы** | **повторяющиеся** фразы схлопываются в один ключ | ⚠️ net-negative только для дублей; уникальную однострочную подпись оставить инлайн; удаление оригинала — в том же коммите; i18n-плагин без рантайм-локали не тащить |
| **Промпты/шаблоны как данные** | повторяющиеся блоки → один шаблон | Rule of Three; одноразовый — не выносить |
| **Атомарный UI-kit** | N копий разметки → 1 атом со слотами | не создавать ради одного места; не плодить god-компонент с булевыми флагами |
| **Устранение дублей и мёртвого кода** | клоны (CPD/jscpd), недостижимый код (detekt/knip/ts-prune) | публичный dead code в одномодульном проекте виден только IDE-reachability; entry-points из удаления исключить |
| **Фабрики инфраструктуры** | N мест создания клиента/парсера → однострочники | заодно сходятся разъехавшиеся таймауты/настройки |

**Гейт:** net-LOC не вырос, dup% ↓, число смелов ↓ — иначе PR откатывается. LOC читать **в паре** со смелами и ревью.

## Стадия 4 — Модуляризируй тонко (контр-приёмы против «модули = +код»)

- **Convention plugins в `build-logic`** (или аналог): per-module build ≈ 5 строк вместо ~40. Вводить **до** первого раскола, когда модулей ≥3.
- **Единый каталог версий** (`libs.versions.toml` / workspace-deps): версии в одном месте.
- **`internal`/`implementation` по умолчанию;** наружу (`api`/`public`) — только реально межмодульное. Меньше поверхность → быстрее пересборка.
- **api/impl split — НЕ вводить**, пока нет ≥2 потребителей или измеримой боли сборки (BSSN/YAGNI).
- **Никаких barrel/re-export** файлов — LOC ради индирекции, циклы, сломанный tree-shaking.
- **Правильная гранулярность:** старт с 4–6 модулей, дробить strangler-fig'ом по мере надобности — не «всё сразу».
- **Резать по доменному смыслу/причине изменения (CCP), а не по слою** (`controllers/services/repositories` — антипаттерн, рвёт common closure).

**Границы держит машина, а не ревью** (обязательный CI-гейт):

| Стек | Инструмент границ |
|---|---|
| Kotlin/JVM, Android | **Konsist**, **ArchUnit**, `module-graph-assert`, detekt |
| Web (FSD) | **Steiger** (`forbidden-imports`) |
| Web (слои) | **eslint-plugin-boundaries**, **dependency-cruiser** (`no-circular`, `no-domain-to-ui`) |
| Web (монорепо) | **Nx** `@nx/enforce-module-boundaries` (теги `scope:*` × `type:*`), **Turborepo boundaries** |
| Backend-JVM | **ArchUnit**, **Spring Modulith** `.verify()` |
| iOS | граф SPM-пакетов, **Tuist** |
| Flutter/Dart | **Melos**, `import_lint` |

## Рой агентов: как скилл строит план (оркестрация)

> Каждый субагент обязан идти **index-first** (см. «Навигация»): `outline`/`usages`/`unfold` вместо чтения
> файлов целиком. Это множит охват — при −85% на чтение за тот же бюджет запускаешь больше агентов или
> картируешь весь god-object разом, а не по кускам.

Для крупной задачи скилл разворачивает субагентов тем же паттерном, что породил этот документ — **три фазы**:

```
Фаза «Исследование» (параллельно):
  • внутр. структура репо  — реальные границы по change-coupling + рёбра зависимостей (Bash/git/grep)
  • практики целевой платформы (из стадии 1) — канон + инструменты границ
  • борьба с разбуханием — токены/строки/дедуп/детекторы, с замерами по этому репо
  • порядок рефакторинга — Mikado/Feathers/branch-by-abstraction под конкретный god-object
Фаза «Синтез»:
  • архитектор — из исследований собирает граф модулей + цепочку шагов + таблицу платформы (schema)
Фаза «Проверка»:
  • критик — АТАКУЕТ план: BSSN/CUPID (не переусложнил ли), правило зависимостей (циклы/feature→feature),
    честность флагов «шаг реально сокращает код / оставляет проект собираемым»
```

Ключевое правило: **критик обязателен.** В прогоне на этом проекте архитектор предложил 13 модулей —
критик срезал до 6–7 как оверинжиниринг, поймал ложное «net-negative» на уникальных строках и дыры в
таблице платформ (Electron/Tauri, Library/CLI). Один проход без адверсариального разбора дал бы
правдоподобный, но раздутый план. Схема одного research-агента (JSON Schema): `patterns[]` (name/whatItIs/
whenToUse/**whenNotToUse**/authority), `moduleBoundaryRules[]`, `codeGrowthCounters[]`, `pitfalls[]`, `citations[]`.

## Стоп-правила (прививка от карго-культа)

- **BSSN** (Best Simple System for Now): рефакторь там, где боль **уже есть**; никаких модулей/интерфейсов/слоёв «на будущее».
- **CUPID:** имя нового модуля/класса доменное (`RagPanelState`), а не техническое (`StateManagerHelper`). Дробление ради дробления создаёт швы, которые придётся перерезать.
- **Несколько модулей/адаптеров не нарушают Clean Architecture** — правило зависимостей про направление, «circles are schematic».
- **Порт делить по назначению, а не по технологии:** один `LlmGateway` с адаптерами cloud/local — верно; `CloudGateway`/`OllamaGateway` под каждого вендора — ошибка (Cockburn).
- **Не всё под снос:** найди уже здоровые части, объяви их эталоном стиля для рефакторинга.
- Каждый шаг оставляет проект **рабочим**; порядок — от механического-безрискового к структурному.

## Формат вывода скилла

1. **Вердикт** (2–4 предложения, честно, без комплиментов).
2. **Таблица метрик** с доказательствами (`file:line`).
3. **Определённая платформа** + выбранная целевая архитектура (со ссылкой на сигналы).
4. **Нарушения** по принципам: что / `file:line` / чем вредит / как чинить.
5. **Что здорово — не трогать** (эталон стиля внутри проекта).
6. **Цепочка шагов** (Mikado-порядок): для каждого — эффект, `↓LOC?`, `оставляет собираемым?`, риск; от механического к структурному.
7. **Граф модулей** (если модуляризация) + правило CI-гейта границ.

## Чек-лист ревью (короткая версия)

- [ ] Класс/модуль держит одну причину изменения? Кто заказчик изменений (SRP по акторам)?
- [ ] Определена платформа по сигналам, а не по предположению? Разрешены конфликты сигналов?
- [ ] Состояние живёт как можно ниже и умирает вместе со своим UI (`sealed ActivePanel`, не `*Open`-флаги)?
- [ ] Тройки `loading+error+result` схлопнуты в `Async<T>`/`Result`-тип?
- [ ] Все реализации интерфейса честно поддерживают контракт (нет молчаливого игнора параметров)? default-параметры не маскируют жирный порт?
- [ ] Потребители не даункастят порт до конкретного типа (протечка абстракции)?
- [ ] Повторяющийся каркас встречается >2 раз (Rule of Three)?
- [ ] Функция ≤ 60 строк, вложенность ≤ 4, в разметке нет вычислений?
- [ ] Composition root ровно один? UI/держатель не конструирует IO/клиентов?
- [ ] Домен/ядро без импортов инфраструктуры/фреймворков?
- [ ] Дубли и мёртвый код убиты **ДО** проведения границы модуля?
- [ ] Границы гейтятся в CI (Konsist/ArchUnit/Steiger/Nx…), а не только на ревью?
- [ ] Абстракция/модуль вводится под **существующую** боль, а не «на будущее» (BSSN)?
- [ ] net-LOC не вырос; dup% и смелы — вниз?
