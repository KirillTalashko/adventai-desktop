# RAG Reranking & Filtering — улучшенный поиск (День 23)

Второй этап после bi-encoder-поиска: **реранк + фильтр релевантности + query rewrite** и «боевая» третья
стратегия chunking. Улучшенный RAG поверх Дней 21–22.

> Индексация — `RAG_INDEXING.md`. Первый RAG-запрос — `RAG_ANSWERING.md`. Теория — `.claude/WEEK_5_RAG.md`.

## Двухэтапный пайплайн

```
question
  → (опц.) query rewrite (LLM)         разговорный вопрос → поисковый запрос
  → embed → bi-encoder top-N (=12)      широкий пул кандидатов
  → RERANK                              эвристика (cosine + лексика) ИЛИ LLM-реранкер
  → ФИЛЬТР по порогу (floor=0.50)       отсечь нерелевантное (score < порога)
  → top-K (=4)                          в контекст LLM
```

Реализация: `domain/rag/Reranker.kt` (`HeuristicReranker`, `LlmReranker`, `RelevanceFilter`,
`QueryRewriter`, `RagOptions`, `RetrievalTrace`), оркестрация — `KnowledgeIndex.retrieve/answerWithTrace`.

## Третья стратегия — `contextual` (боевая, по умолчанию)

`domain/rag/Chunker.kt · ContextualChunker`. Лучшее из structural+fixed + **contextual retrieval**:
- границы **по заголовкам** (никогда не режем поперёк раздела);
- внутри крупного раздела — окно слов с **overlap** (баланс размера);
- **в текст каждого чанка добавляются хлебные крошки «документ › раздел»** — чанк эмбеддится ВМЕСТЕ с
  темой, поэтому поиск понимает, о чём кусок.

Именно это вытащило промахи Дня 22 (#4 «отказ США», #5 «ОАЭ»): нужный документ теперь поднимается ещё
на этапе поиска. `contextual` — стратегия по умолчанию для ответов; `fixed`/`structural` остались для сравнения.

## Реранк (2 варианта, тумблер)

- **Эвристика** (по умолчанию, детерминированно, без сети): `score = 0.5·cosine + 0.5·lexical`, где
  `lexical` — доля основ слов запроса (лёгкий русский стеммер), встретившихся в чанке. Даёт буст документу
  с реальными словами запроса и душит «похоже по вектору, но не по теме».
- **LLM-реранкер** (опц.): модель возвращает номера строго релевантных фрагментов; невыбранные отсекаются.

## Фильтр и порог

`RelevanceFilter`: оставляем `score ≥ floor`, затем top-K. Порог настраивается слайдером (по умолчанию
**0.50**). На релевантных запросах фильтр почти не режет (recall сохраняется), а на вопросе-ловушке
(«Северный полюс») лексическое пересечение ≈ 0 → комбинированный score ниже порога → **выдача пустеет →
честный отказ уже на этапе поиска**.

## Query rewrite (тумблер, LLM)

`QueryRewriter`: переписывает разговорный вопрос в короткий поисковый (страна, тип визы, суть) перед
эмбеддингом — помогает bi-encoder на «живых» формулировках. Трейс показывает «было → стало».

**Наглядный статус (под тумблером).** `QueryRewriter.rewrite` возвращает `RewriteResult(query, failed)`, а
`retrieve()` выводит `RewriteOutcome` (`OFF` / `REWRITTEN` / `UNCHANGED` / `FAILED`) в трейс. Под тумблером
видно, что случилось на последнем прогоне: **переписал ‹было›→‹стало›**, **вернул то же** (вопрос уже
краткий) или **вызов не удался** (сеть/лимит — красным). Раньше сбой сети маскировался под no-op: rewrite
`getOrNull() ?: question` молча отдавал исходный запрос, и «упал» было не отличить от «нечего менять».

## Детектор отказа (`ragLooksLikeRefusal`)

Отличает **честный отказ** («в базе нет данных») от обычного ответа — чтобы для вопроса-ловушки честно
подписать, почему показаны нерелевантные фрагменты. Матчит **только** мета-фразы об отсутствии *данных* в
*базе/контексте* (как велит `RAG_SYSTEM`), а не любое «нет»/«отсутствует» внутри самого ответа: иначе живые
фразы базы («апелляции **нет**», «баланса **нет**», «справка об **отсутствии** судимости») ложно давали
плашку «нет данных» поверх нормального ответа. Грабля регэкспа: `\w` в Java матчит только ASCII (мимо
кириллицы), а `IGNORE_CASE` без `UNICODE_CASE` не сворачивает регистр — решается через `\p{L}` и `(?iu)`.

## Сравнение «без фильтра vs с фильтром»

Детерминированное (без LLM, если rewrite выкл): baseline = **как в Дне 22** (структурная стратегия, сырой
top-K по cosine); improved = **contextual + реранк + фильтр**.

**Проверено на реальной Ollama (14 док., 103 контекстных чанка):**
- нужный документ найден: **baseline 6/9 → improved 9/9** (#2, #4, #5 починены);
- на ловушке: **baseline 4 фрагмента → improved 0** (отсечены → отказ);
- порог 0.50 — оптимум (recall 9/9 и негатив → 0).

## Как посмотреть (dev-панель «Индексация знаний (RAG)»)

1. `.\gradlew.bat run` → режим разработчика (+ ключ LLM). Композер → иконка-БД.
2. **Шаг 1** — «Построить индекс» (строятся все 3 стратегии; таблица со сравнением).
3. **Шаг 2** — блок **«Улучшенный поиск»**: стратегия / реранк / query rewrite / порог. Задать вопрос →
   «Спросить в обоих режимах» → под ответом виден **трейс: top-K ДО (cosine) и ПОСЛЕ (реранк+фильтр)**.
4. **Шаг 3А** — «Сравнить поиск (без/с фильтром)»: сводка recall и отсев на ловушке (без LLM).
   **Шаг 3Б** — «Прогнать ответы (10 вопросов)»: сравнение ответов с RAG / без RAG.
