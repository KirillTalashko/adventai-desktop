# Ассистент разработчика (День 31)

Команда **`/help`** в чате: агент отвечает на вопросы **об этом проекте**, опираясь на его собственную
документацию (RAG) и на **живой контекст репозитория** (git через MCP).

Это отдельный «режим» внутри того же приложения: визовый агент остаётся визовым, а `/help` работает
по своему индексу, своему MCP-серверу и своему промпту.

---

## Что умеет

| Команда | Что делает |
|---|---|
| `/help` | справка: что умею, состояние индекса и какие файлы в корпусе |
| `/help index` | (пере)индексировать документацию проекта |
| `/help <вопрос>` | ответ по докам проекта + текущая git-ветка; внизу — список файлов-источников |

Вопрос, на который нет ответа в документации, получает **честный отказ** — LLM в этом случае не
вызывается вообще, поэтому ответ невозможно спутать с общими знаниями модели.

---

## Три составные части

### 1. RAG по документации проекта — `data/ProjectDocsIndex.kt`

Отдельный индекс (`~/.adventai/devdocs/devdocs.db`), не смешивается с визовой базой знаний.
Корпус читается **живьём из репозитория** (не копируется), поэтому после правки доков достаточно
выполнить `/help index`.

Что попадает в корпус:
- `README.md` и остальные `*.md` в корне (`CLAUDE.md`, `RAG_*.md`, `LOCAL_LLM.md`, `LLM_SERVICE.md` …);
- вся markdown-документация из каталога `.claude` (архитектура, память, контекст, MCP, RAG, инварианты, конвенции);
- файлы-схемы данных: `domain/Model.kt`, `domain/CaseFile.kt`, `data/Dto.kt`.

Пайплайн переиспользует уже готовое: `ContextualChunker` → `DocumentIndexer` → `SqliteIndexStore`,
поиск — **двухступенчатый отбор**: `RagSearch` (пул 20) → порог по близости → `LlmReranker` → top-K.

**Почему две ступени, а не одна.** Тут не сработал ни один из очевидных вариантов по отдельности:

- **Только порог** — оценка есть `0.5·косинус + 0.5·лексика`, и она несопоставима между формулировками.
  Один и тот же чанк `CLAUDE.md` давал **0.46** на русский пересказ («правило про кликабельные элементы»)
  и **0.79** на точные термины (`Surface`, `onClick`). Любой фиксированный порог либо режет нужное, либо
  пропускает лишнее.
- **Только LLM-реранк** — маленькая локальная модель **всегда что-нибудь выбирает** и не умеет ответить
  «ничего не подходит». На заведомо постороннем вопросе (биллинг Stripe) она отобрала случайные чанки, и
  честный отказ превратился в воду с домыслами.

Поэтому каждая ступень делает то, что умеет: **порог** отвечает «есть ли в доках хоть что-то по теме»
(замер: 0.62 у лучшего чанка по вопросу из доков против 0.36 по постороннему — разделение уверенное),
а **модель** выбирает из оставшегося то, что действительно отвечает. Пусто после первой ступени →
LLM не вызывается вовсе → честный отказ гарантирован кодом.

### 2. Живой контекст проекта через MCP — `mcp/DevMcpServer.kt`

Свой локальный MCP-сервер (stdio-подпроцесс, как визовый). Все инструменты **read-only**:

| Инструмент | Что возвращает |
|---|---|
| `git_current_branch` | текущая ветка (минимум по заданию дня) |
| `git_status` | короткий статус рабочего дерева |
| `list_files` | файлы под контролем git, с необязательным фильтром по подстроке пути |

Корень проекта — env `PROJECT_ROOT`, иначе рабочий каталог процесса.

### 3. Команда `/help` — `domain/DevAssistant.kt` + `ui/ChatState.kt`

`DevAssistant` (чистый домен) складывает три источника: фрагменты доков, git-ветку и LLM.
Домен не знает ни про SQLite/эмбеддеры, ни про MCP SDK — только лямбды-порты.

```

```

## Проверка

```powershell
.\gradlew.bat runDevMcp     # dev-MCP: ветка, статус, файлы проекта
.\gradlew.bat runDevHelp    # весь /help в консоли (нужна Ollama)
.\gradlew.bat run           # в приложении: /help index, затем /help <вопрос>
```

`runDevHelp` требует `ollama serve` + модели `nomic-embed-text` (эмбеддер) и `qwen2.5:7b` (генерация).
Набор вопросов по умолчанию включает **негативный контроль** — вопрос, которого нет в документации.
Индекс переживает перезапуск, поэтому строится один раз; повторить принудительно — `--args="--reindex"`.

⚠️ **Индексация — разовый шаг настройки, а не часть демо.** Корпус (33 документа, 378 чанков) считается
локально на CPU и занимает **несколько минут**: батч-эндпойнт и параллелизм убирают накладные расходы, но
упор идёт в вычисления, а не в задержку сети. Перед записью видео индекс нужно построить заранее — тогда
`/help` отвечает сразу.

## Решения и грабли

- **Отдельный индекс, а не общий с визовым.** Смешивать доменную базу знаний и техдоки нельзя: поиск
  начал бы возвращать архитектуру в ответах про визы и наоборот.
- **Отдельный MCP-гейтвей.** `/help` обязан работать независимо от переключателей MCP-панели, поэтому у
  ассистента свой `devToolGatewayFactory`, а не общий с визовым сервером.
- **LLM не вызывается при пустом retrieval.** Так честный отказ гарантирован кодом, а не уговорами в промпте.
- ⚠️ **Вложенные комментарии Kotlin.** Последовательность `/*` внутри KDoc (например в пути вида
  `.claude/` + `*.md`) **открывает вложенный комментарий** и роняет файл с «Unclosed comment». В комментариях
  такие пути надо разбивать.
- ⚠️ **Deadlock на выводе подпроцесса.** Читать `process.inputStream` нужно **до** `waitFor`: при большом
  выводе (`git ls-files` — сотни путей) дочерний процесс блокируется на переполненном pipe-буфере ОС, и
  ожидание уходит в таймаут. Симптом был тихий — `git_status` (короткий вывод) работал, а `list_files`
  возвращал пусто.
- ⚠️ **Эмбеддинг — сетевой вызов.** Последовательный цикл по сотням чанков (~0.5 c каждый) складывается в
  минуты. В `DocumentIndexer` эмбеддинги считаются **пачками и параллельно** (`async` + `awaitAll`, порядок
  сохраняется; `Semaphore` ограничивает одновременные запросы). Ускорило и визовый индекс тоже. Но упор в
  итоге идёт в CPU, а не в сеть — индексация всё равно занимает минуты (см. выше).

### Три «тихих» дефекта, найденных ревью

Все три не роняли сборку и не выдавали ошибок — они **врали пользователю**. Такое ловится только разбором.

- ⚠️ **Код возврата подпроцесса важнее его вывода.** `git` пишет `fatal: …` в stderr и выходит с кодом 128,
  а stderr был слит в stdout — без проверки `exitValue()` эта строка уезжала в ответ **как имя ветки**
  («🌿 Ветка проекта: `fatal: not a git repository`»). Хуже всех был `list_files`: единственная строка
  ошибки не совпадала с фильтром, и инструмент бодро отвечал «Файлов: 0» — неотличимо от честного пустого
  результата. Теперь `runCommand` возвращает `CommandResult(ok, output)`, и ошибка никогда не выглядит как данные.
- ⚠️ **Сбой поиска ≠ «в документации нет».** `DevAssistant` глушил исключение ретривера и отдавал
  `NOT_IN_DOCS`. То есть при неподнятой Ollama пользователь получал уверенное «я этого не нашёл, отвечать
  общими знаниями не буду» — ложное утверждение о корпусе. Теперь сбой пробрасывается и показывается как
  ошибка, а пустой результат по-прежнему означает честное «не нашёл».
- ⚠️ **Вектора разных эмбеддеров несопоставимы, и размерность это не поймает.** Эмбеддер запроса брался из
  тумблера RAG-панели, а не из индекса. Переключил тумблер после индексации — и запрос кодируется другой
  моделью; у `OllamaEmbedder` и `HashingEmbedder` одинаковые 768, поэтому проверка размера в `VectorMath`
  не срабатывает, косинус считается «успешно» и даёт мусор. Симптом тихий: `/help` отвечает «в документации
  этого нет» на вопрос, который там есть. Теперь эмбеддер запроса восстанавливается из `stats().embedderId`.
